# Doctor verification: investigation and Firebase owner steps

Branch inspected: `Auchithya`. Existing uncommitted work was preserved. No cloud
data, Auth accounts, deployed rules, or Git remotes were changed.

## Cause and limits

The reported access message maps to Firebase `permission-denied` on the complete
`users` collection listener. When this followed a cached snapshot, the controller
kept the pending doctor and cache flag, displaying both reconnect and permission
warnings. The disabled review button correctly blocked writes. The new Flutter
regression reproduces that sequence. Reconnection alone cannot fix denied access.

Registration and review both use `users/{Firebase Auth UID}`; there is no separate
registration collection. Live mode never substitutes demo records. Fictional
records are seeded only in explicit preview mode. All platform configurations
reference project `opd-connect`, number `485137437849`.

Login routes active `role: "admin"` profiles through its verification gate to
the workspace. Workspace permissions now come from an independent listener to
that UID's own profile, so denied directories cannot hide a missing role.
Missing `staffRole` previously defaulted to `Hospital administrator`;
it now grants no management access. Reviews require an active admin profile,
`isVerified: true`, and an explicit `Hospital administrator` or
`Super administrator` role. Support coordinators retain read access. Custom
claims and alternative role spellings are not used by this app.

The follow-up read-only browser inspection confirms a valid token for the
correct project, a readable own profile missing `staffRole`, and HTTP 403
`PERMISSION_DENIED` on users/settings/activity. The deployed policy remains
unavailable without owner access. See [the confirmed data-access cause and exact owner steps](ADMIN_DATA_ACCESS_SETUP.md).
An emulator pass is not deployed-policy verification.

## Fix

Denied/expired account reads clear cached profiles and show `Access denied`.
Disconnected/cache states keep clear connection messages. Failed queues no longer
claim all reviews are complete. Review buttons require management permission and
live data; dialogs update controls and warnings if access/connectivity changes.
Both approval checkboxes are required. Rejection requires a trimmed reason of at
least eight characters, preserving the existing workflow.

Review decisions now use a transaction that verifies the current pending doctor
and saves the decision and activity atomically. Offline transactions fail, and
concurrent/stale reviews cannot overwrite completed decisions. Profile fields:
`isApproved`, `isVerified`, `approvalStatus`, `reviewNote`, `reviewedBy`,
`reviewedAt`, `identityChecked`, `credentialsChecked`, `reviewReason`, and
`reviewActivityId`. Linked activity fields: title, detail, actor name, `actorId`,
`targetId`, decision, reason, and server `time`. Actor names come from the current
profile; both timestamps are generated by Firestore.

Normal startup no longer queries/provisions administrators from client `.env`
credentials. Provisioning belongs to the owner. The unused seed helper remains.

## Exact owner steps

1. In Firebase console **opd-connect → Authentication → Users**, find the intended
   administrator by email. Copy the UID and confirm the Auth account is enabled.
   Do not share passwords or ID tokens.
2. In the `(default)` **Firestore Database → Data**, inspect **users/{that UID}**.
   An authorized owner should provision/correct only that intended administrator,
   preserving unrelated fields:

   ```json
   {
     "name": "Administrator display name",
     "role": "admin",
     "staffRole": "Hospital administrator",
     "isActive": true,
     "isVerified": true
   }
   ```

   Use `Super administrator` only for the designated owner if intended. Console
   IAM ownership does not assign an app role. An email-named document instead of
   the Auth UID will not grant access.
3. Inspect **users/{doctor Auth UID}**: `role: "doctor"`, `isActive: true`,
   `isApproved: false`, `isVerified: false`, `registrationNumber`, and `department`.
   Preserve rejected decisions; they are not pending. Confirm identity before
   correcting any misplaced legacy records.
4. Save/export deployed rules first. Review **firestore.verifications.rules** as
   a tested reference for this single-hospital workflow. It permits complete
   `users` queries only to active verified staff with explicit roles; reviews
   only to hospital/super administrators; and reads of `staff_activity` and
   `hospital_settings/default` to staff. It enforces pending-only transitions,
   checkbox flags, meaningful rejection reasons, actor identity, server times,
   and immutable linked audit entries in the same atomic write. Verified email
   patients/doctors can self-register without provisioning administrator access.
5. Merge those conditions into the existing policy and preserve other modules.
   **Do not blindly deploy the reference file over existing rules.** It supplies
   no generic account edits, staff-role management, hospital-settings writes, or
   clinical/booking permissions; those require separate secured rules. Exclude
   all review fields listed above from other profile-update permissions and
   prevent self-promotion. Remove overlapping broad allow clauses that bypass
   these checks: Firestore allow clauses are additive. Never grant collection
   access to all signed-in users. Multiple hospitals need hospital-scoped
   authorization and queries before using this policy.
6. Test the merged policy in the emulator, then publish the reviewed rules in
   **Firestore Database → Rules**. Sign out/in and Retry. Validate authorized
   reads, denied roles, two-checkbox approval, rejection reasons, and linked
   reviewer/timestamp activity. If the deployed policy already permits these
   requests, check App Check enforcement, the actual project/database, and
   request-denial diagnostics before changing permissions.

Repository evidence indicates no required change to `firebase_options.dart`.
Email/password Auth must remain enabled. Production validation is an owner step.

## Tests

Recorded results: **38 Flutter tests passed**, **30 Firestore emulator tests
passed**, and the scoped Flutter analyzer reported **no issues**. The emulator
suite includes successful decisions, denied roles, both confirmation flags,
rejection validation, forged audit data, legacy pending registrations, and two
concurrent transactions producing exactly one decision/activity entry. Expected
permission-denied logs during negative tests are intentional. These results
validate the local rule reference, not the deployed Firebase project.

From the repository root:

```powershell
flutter test
flutter analyze lib/staff lib/main.dart test lib/widgets/auth_wrapper.dart
```

From `firebase` with Node 22+ and Java 21+:

```powershell
npm.cmd ci
npm.cmd test
```

The separate `firebase/firebase.json` is for emulator tests; root Flutter Firebase
configuration is unchanged. Tests use **demo-opd-connect** on `127.0.0.1:8088`,
never deploy rules or write to production. The lockfile pins test dependencies.
Flutter tests exercise the actual controller/UI. JavaScript emulator tests
validate server authorization, transaction writes, audit timestamps, and
concurrent decisions.
